# 앱 경량화 (저사양 Android 폰) — 2026-10-20

브랜치 `perf/app-lite` (기준 `fix/stream-commit-race` `364b3f0`). 대상 사용자는 값싼 Android 폰을 쓰므로
**JS 번들 크기, 통화 중 프레임당 작업량, 다시 그리기 횟수, 메모리**를 줄였다. 실기기가 없어 **정적 분석 + 번들 내보내기 + 웹 e2e** 로만 확인했다.
측정은 모두 이 Mac 에서 `npx expo export` 로 했고, 네이티브 빌드·프로파일링은 하지 않았다 (아래 4절).

### 1-3. 통화 화면 상태 갱신·다시 그리기 횟수 (추정, 코드 분석)

통화 화면 `frontend/src/app/site/call/[id].tsx` 는 `useStreamingCall`/`useHandsFree` 의 state 가 바뀔 때마다 **화면 전체**(머리글·상태·자막·FlatList 의 보이는 말풍선 전부)를 다시 그렸다.
`renderItem` 이 매번 새 화살표 함수였고 `MessageBubble` 이 memo 가 아니어서 FlatList 의 보이는 행도 모두 함께 다시 그려졌다.

| 원인 | 전 (화면 전체 다시 그리기 / 초) | 후 |
|---|---|---|
| 마이크 음량 `setLevel` (스트리밍: 100ms 조각마다 / 발화 단위: 100ms 타이머) | **10회/초, 통화 내내** (말하지 않아도 잡음으로 값이 흔들림) | **0회** — 음량은 `audio/micLevel` 저장소에 쓰고 음량 막대 `MicMeter` 하나만 `useSyncExternalStore` 로 구독. 1/20 단계 양자화 + 10Hz 상한이라 막대 갱신 ≤ 10회/초, 그것도 값이 달라질 때만 |
| 상대 자막 글자 조각 `stream:out:text` (OpenAI 번역 전사 delta, 토큰마다) | 약 10–30회/초 (상대가 말할 때) | ≤ 10회/초 — 100ms 창으로 모아 setState 1번 (`audio/batchedState`) |
| 내 말 자막 조각 `stream:mine:text` (받아쓰기 partial·번역 delta) | 약 5–20회/초 (내가 말한 뒤) | ≤ 10회/초 (같은 방식) |
| 턴 시작·끝, 말 시작·끝, 재생 시작·끝 | 턴당 수 회 | 동일 (순서가 중요해 즉시 적용, 앞서 모인 조각은 먼저 flush) |
| **합계 (양쪽이 말하는 구간)** | **약 25–60회/초 화면 전체** | **약 10–20회/초 화면 일부** — 게다가 `MessageBubble`·`MicStatus`·`DeviceChip`·`ModeChip`·`LiveCaptions`·`MyCaptions` 는 memo + 안정된 콜백이라 입력이 바뀐 부품만 그린다 |
| 발화 단위 통화·일괄 지시 (핸즈프리) | 10회/초 화면 전체 (음량) | 0회 (음량 막대만) |

예: 60초 통화에서 양쪽이 반씩 말하면 전에는 화면 전체 다시 그리기 약 1,500–2,500회, 후에는 자막 부품 약 300–600회 + 음량 막대 ≤ 600회(작은 View 1개).

## 2. 바꾼 것

### 2-1. 통화 화면 다시 그리기 (frontend/src/audio, components, app/site)

- `src/audio/micLevel.ts` (새 파일): 마이크 음량 외부 저장소. `setMicLevel`/`setMicLevelDb` 로 쓰고, `subscribeMicLevel`/`getMicLevel` 로 구독. 1/20 양자화, 알림 10Hz 상한.
  `useStreamingCall`·`useHandsFree` 는 `setLevel` 대신 이 저장소에 쓴다 (훅 반환값에서 `level` 제거).
- `src/audio/batchedState.ts` (새 파일): reducer 를 창(100ms) 안에 모아 한 번의 setState 로 적용. `queue`/`flush`/`clear`.
  `useStreamingCall` 에서 상대 자막(`stream:out:text`)·내 말 자막(`stream:mine:text`) 조각에 사용. 턴 시작·끝·내 말 시작/끝은 `flush` 후 바로 setState 해 순서를 지킨다. 화면을 떠나면 `clear`.
- `useStreamingCall`: 100ms 조각마다 만들던 `send` 클로저를 effect 밖으로 올렸다 (조각당 할당 제거).
- `components/live/LiveParts.tsx`: `MicStatus` 에서 `level` prop 제거, 안에 `MicMeter`(저장소 구독) 추가. `MicStatus`·`DeviceChip` 을 `memo`.
- `components/chat/MessageBubble.tsx`: `memo`. `onRetry` 서명을 `(messageId) => void` 로 바꿔 부모가 안정된 콜백 하나를 넘긴다 (`NO_RETRY` 상수 제공). 재생 중 표시는 `playingId === message.id` 만 구독해 다른 메시지 재생 때 다시 그리지 않는다.
- 통화 화면: `LiveCaptions`·`MyCaptions`·`ModeChip` 을 `memo`, `renderItem` 을 `useCallback`, `keyExtractor`·`contentContainerStyle` 모듈 상수, FlatList `initialNumToRender=8 maxToRenderPerBatch=6 windowSize=5` (기본 windowSize 21 = 화면의 10배를 미리 그림 → 저사양 폰 메모리·작업 절감).
- 대화 화면: `renderItem`·`retryMessage` 를 `useCallback`, FlatList `initialNumToRender=12 maxToRenderPerBatch=8 windowSize=7`.
- 일괄 지시 화면: `SpokenItem` memo, `renderItem` 모듈 상수/`useCallback`, 같은 FlatList 옵션.
- 행 높이가 글자 수에 따라 달라 `getItemLayout` 은 쓰지 않았다. `removeClippedSubviews` 는 inverted 목록에서 Android 빈 화면 보고가 있어 넣지 않았다 (실기기에서 확인 후 켤 것).

### 2-2. 번들 (frontend/package.json, app.json)

## 4. 하지 않은 것 (실기기·빌드 필요)

- **실기기 프로파일링**: 프레임 시간, 실제 다시 그리기 횟수(React DevTools Profiler), 메모리(Android Studio Profiler), 시작 시간. 1-3절 수치는 코드 분석으로 추정한 것이다. Galaxy S22 보다 낮은 급(예: Galaxy A1x, 3–4GB RAM, Android 10–12)에서 통화 60초 동안 `adb shell dumpsys gfxinfo <package>` 의 janky frames 비율과 `dumpsys meminfo` 를 전·후로 재볼 것.
- **릴리스 빌드**: `expo-build-properties` 의 Proguard·shrinkResources 는 `expo run:android --variant release` 로 빌드해 (1) 빌드 성공, (2) 앱 실행·로그인·통화·QR·카메라 스캔이 되는지 확인해야 한다. 반사(reflection)를 쓰는 라이브러리가 깨지면 `android/app/proguard-rules.pro` 에 keep 규칙을 추가한다 (Expo 모듈은 자체 규칙을 가지고 있어 대개 문제 없다).
- **Supabase 인증 교체의 실서버 확인**: `npm run bundle:web:live && npm run e2e:live` (실제 Supabase 계정 + `ENGINE=fake` 서버) 로 로그인·비밀번호 재설정 링크(`handleAuthRedirect`, PKCE `exchangeCodeForSession`)를 확인할 것. 이 작업에서는 서버를 띄우지 않았다 (지시: 서버·AWS 없음).
- `vad.ts` 는 손대지 않았다 (`vad-refactor` 작업과 겹침). 현재도 조각당 할당은 없고(이벤트 때만 객체 생성) 수학은 스칼라 연산뿐이라 저사양 폰에서 문제 되지 않는다. 네이티브 → JS 조각 전달의 base64 디코딩·`levelDbOf` (`audio/duplex/native.ts`) 는 `perf-network` 작업 몫.

## 5. 권장 사항

- **최소 Android 버전**: Expo SDK 57 / RN 0.86 의 기본 `minSdkVersion` 은 24 (Android 7.0, Expo 문서 기준 — 빌드 전 `expo-build-properties` 의 `android.minSdkVersion` 으로 확인). 블루투스 SCO·`AudioRecord` voice_communication 경로와 Hermes 는 API 24 에서 동작하지만, 실제로 시험한 최저 기기는 Galaxy S22(Android 14) 뿐이다. **배포 전 Android 10(API 29) 급 저가 기기 1대**를 기준 기기로 정해 S3·S4 시험에 넣을 것. API 26 미만 기기는 블루투스 헤드셋 경로(`setCommunicationDevice` 는 API 31+, 이하는 `startBluetoothSco`) 때문에 지원 범위에서 빼는 것을 권한다.
- **Hermes 유지** (`jsEngine: "hermes"`). JSC 로 바꾸지 말 것 — 저사양 폰에서 시작 시간·메모리가 Hermes 가 유리하다.
- **릴리스 플래그**: Proguard + shrinkResources (이번에 설정). 추가로 EAS 빌드라면 `android.buildType: "apk"` 보다 AAB 로 올려 기기별 분할(ABI·밀도)을 받게 하고, 로컬 APK 는 `--variant release` 로만 배포한다 (개발 빌드는 Metro·디버그 코드가 들어 있어 비교 대상이 아니다).
- **다음 번들 후보** (이번에 측정만 하고 바꾸지 않음):
  - `src/i18n/strings.ts` 88 KB: 언어별 파일로 나누고 선택 언어만 `require` 하면 약 70 KB 절감. UI 언어를 바꿀 때 비동기 로딩이 필요해 보류.
  - 데모(mock) 서비스 약 35 KB (`mockDb`·`mockApi`·`phrases`): `services/index.ts` 가 두 구현을 모두 정적 import 해 live 빌드에도 들어간다 (`EXPO_PUBLIC_API_MODE=live` 로 내보내도 크기 동일 — 측정함). Metro 는 `process.env` 분기로 import 를 제거하지 않는다. 빌드 시 `EXPO_UNSTABLE_METRO_OPTIMIZE_GRAPH=1` (실험적 트리 셰이킹) 을 켜면 빠질 수 있으나 실기기 검증 없이는 켜지 않았다.
  - `babel-preset-expo` 의 `lazyImports: true`: 모듈 평가를 첫 사용 시점으로 미뤄 **시작 시간**을 줄인다. 번들 크기는 그대로. Expo 기본 Metro 설정은 `inlineRequires: false` 라 지금은 모든 모듈을 시작 때 평가한다. 부작용(모듈 평가 순서) 위험이 있어 실기기에서 시작·통화·QR·카메라를 확인하며 켤 것. 웹 빌드에는 적용되지 않아 e2e 로는 검증이 안 된다.
  - `react-native-worklets`(97 KB) + `@expo/ui`(65 KB): expo-router 의 Android 네이티브 툴바가 끌어온다. 앱이 안 쓰므로 expo-router 가 선택 의존성으로 바꾸면 빠진다 (상류 이슈 확인 필요).
- **통화 화면 추가 개선 후보** (실기기 측정 후): `removeClippedSubviews` (Android), 자막 창 100ms → 150ms, 음량 막대를 `Animated` 네이티브 드라이버로 옮겨 JS 스레드와 완전히 분리.
