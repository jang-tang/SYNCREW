## 2. 실제 OpenAI 확인 (남은 일 1)

방법: `server/scripts/openai-check.ts`. 관리자 한국어 음성(macOS `say`, Yuna) "안전모 착용하고 2번 프레스 기계 비상정지 버튼을 확인하세요." → STT → domain 보정 → 4개 언어 번역(음성 포함, 실제 기본 설정) → 그 번역 음성을 작업자 발화로 다시 STT → 한국어 번역(텍스트만, 비용 절약). 모델: STT `gpt-4o-mini-transcribe`, 번역 `gpt-realtime-2.1`(reasoning low, voice marin).

### 결과

|---|---|---|

- 첫 실행에서 vi·zh·uz의 "한국어 → 작업자 언어" 번역문과 지연은 출력 전에 uz STT 오류로 멈춰 기록하지 못했다. 두 번째 실행은 그때 저장된 번역 음성을 다시 썼다(`--reuse`). 그래서 ko→vi/zh/uz 번역문은 직접 보지 못했고, 그 음성의 STT 결과로만 확인했다.
- **우즈베크어**: 의미가 바뀌는 오류가 생겼다. 번역(ko→uz) 단계인지 STT 단계인지는 번역문을 기록하지 못해 구분하지 못했다. 안전 지시에 그대로 쓰기 어려운 수준이다. 대책 후보: 현장 데이터셋에 uz 용어·검증 문장 추가, 받은 쪽 화면에 원문 함께 표시(이미 있음), uz STT 모델을 `gpt-4o-transcribe`로 올려 비교(비용 증가).
- 입력 음성이 합성음(`say`, OpenAI 음성)이라 실제 사람·현장 소음에서는 STT가 더 나빠질 수 있다.

### 지연 (이 PC, 집 네트워크)

- STT 0.9–1.9초, 텍스트 번역 2.0–2.9초, 음성 포함 번역 3.1초(7.2초 분량 음성).
- 말 끝 → 상대 이어폰 예상: 발화 끝 감지 0.8초 + 업로드 + STT 1–2초 + 음성 번역 약 3초 + 내려받기 ≈ **5–6초**. 서버를 거친 실제 측정(3절): 업로드 → 상대 수신 5.1초 → 말 끝 기준 약 6초.
- 번역 응답은 음성이 끝까지 생성된 뒤 한 번에 보내므로, 진짜 스트리밍(추후 개선)이 지연을 가장 크게 줄인다.

## 4. 기기 확인 (남은 일 3)

### 실제 말소리 자동 감지 (웹, `npm run e2e:mic`) — 확인

- 헤드리스 Chrome 가짜 마이크에 한국어 음성 파일(말 3초 + 무음 4초 반복)을 넣고, 통화 화면에서 버튼 없이 자동 전송되는지 본다.
- 결과: **"듣고 있어요 → 말하는 중… → 자동 전송 → 상대 응답" 6.3초. 대조군(무음만)은 25초 동안 전송 없음.** 웹 expo-audio의 음량 측정·발화 감지·녹음 구간 전송이 실제 음성으로 동작함을 처음 확인했다.
- 알아낸 점: Chrome은 `--disable-features=AudioServiceSandbox` 없이는 음성 파일을 읽지 못하고 무음을 넣는다 (지난번 에뮬레이터에서 소리가 안 들어온 것과는 별개 원인).

### 추가한 서버 테스트 (31개, 전체 157개 통과)

- **권한 매트릭스** (`permissions.test.ts`): 현장 경로 21개 × {토큰 없음 401, 다른 현장 404, 가입 대기 404, 제외됨 404, 구성원, 관리자}. 같은 표에 "구성원·관리자는 통과" 대조군을 둔다 (쓰기 경로는 부작용을 피하려고 잘못된 본문을 보내 400 = 권한 통과를 확인). 통화 수락·거절은 받는 사람만(건 사람 403), 참여자가 아니면 조회·수락·종료·발화·기록 404. 제외된 사람은 그룹 대화에 보낼 수 없고 `/sync`에 그 현장 메시지가 나오지 않음(대조군: 구성원은 나옴).
  - 변이 검증: 가입 코드 조회를 구성원에게 열면 해당 칸만 실패함을 확인 후 복구.
  - 참고: 지시 완료(`/instructions/:id/complete`)는 본문 검증이 받은 사람 확인보다 먼저라, 잘못된 본문이면 누구에게나 400. 존재 여부를 드러내지 않으므로 그대로 둠.
- **안정성** (`stability.test.ts`): 지시·통화 발화 중복 전송(동시 3회 포함) 1건만 생성 / 음성 2MB 초과 400(대조군 202) / 전송 속도 제한 429, 메시지·지시가 한도 공유, 다른 사용자 영향 없음 / 비용 한도 소진 시 번역 필요한 전송 402·메시지 미생성, 같은 언어끼리는 계속 전송 / 연결 끊긴 동안 온 3건이 실시간으로 오지 않고 재접속 후 `/sync?since`로 빠짐없이 순서대로 / 동시 처리량.
- **처리량** (가짜 번역 1건 100ms, 동시 처리 4): 구성원 8명이 동시에 5건씩 40건 → 접수 108ms, 번역·전달 완료 1,169ms(이론 하한 1,000ms), 40건 모두 한 번씩 전달, 유실·중복 0. 실제 OpenAI(번역 2–3초)라면 동시 4개 기준 초당 약 1.5–2건이 상한이다 → 현장 1곳 규모(수십 명)에는 충분하나, 일괄 지시가 몰리면 `TRANSLATION_CONCURRENCY`를 올려야 한다.
- **우즈베크어 STT 요청 형식** (`openAiEngines.test.ts`).

## 6. 알려진 문제·제약

1. **우즈베크어 통역 품질** — 안전 지시 의미가 바뀜 (2절). 데이터셋·모델 보강 필요.
2. 말 끝 → 상대 이어폰 약 5–6초 (발화 단위 방식의 한계). 진짜 스트리밍은 네이티브 모듈 필요(추후).
3. live 모드는 웹 빌드로만 확인 (네이티브 앱 ↔ PC 서버는 실기기 때).
4. 실기기·블루투스·백그라운드 미검증.
5. 서버 재시작 시 세션 정리(`closeStale`), 시작 시 복구 연결(`index.ts`)은 자동 테스트 없음 (공유 테스트 DB 때문).
6. 서버에 CORS 없음 → 웹 앱으로 운영하려면 추가 필요 (현재 대상은 네이티브 앱이므로 불필요).
7. 업로드 MIME 허용 목록 없음 (모르는 형식은 `.bin`으로 저장 후 디코딩 실패 → `AUDIO_INVALID`). 크기 2MB 제한은 있음.
8. 비용 기록은 추정 단가 기준. 실제 청구액과 대조 필요.
9. iOS에서 시작 화면 로고 "Sync" 글자가 어둡게 보임 (웹 정상, 원인 미조사).
10. 동시 통화 걸기 경합(서로 동시에 걸면 둘 다 울림), 전이중 미지원, 녹음 구간 전환 시 말 앞부분 잘림 가능 (Phase 5에서 알려짐).
