## 1. ① OpenAI Realtime 스트리밍 측정 결과

### 1-1. 방법

- 스크립트: `server/scripts/stream-measure.ts` (재실행: `npx tsx scripts/stream-measure.ts --dry-run`으로 계획·예상 비용 확인 후 실행, DB 필요)
- macOS 합성 음성(ko Yuna, vi Linh, zh Tingting, ru Milena)을 앞뒤 무음을 자른 뒤 24kHz PCM 100ms 조각으로 **실제 말하는 속도**로 Realtime WebSocket에 보냈다. 말이 끝난 뒤에도 응답이 끝날 때까지 무음을 계속 보냈다(통화처럼).
- 세션 설정: `gpt-realtime-2.1`, 출력 음성 `marin` 24kHz, `reasoning.effort = low`(서버 기본값), 입력 전사 `gpt-4o-mini-transcribe`(언어 지정), `create_response: true`, `interrupt_response: false`, 지시문 = 지금 `buildInstructions` + 세션 문장들의 현장 용어집을 미리 포함.
- 시간 기준 "말 끝" = 마지막 말소리 조각을 보낸 시각. 지연에는 **이 PC ↔ OpenAI 왕복 네트워크가 포함**되고, 휴대폰 ↔ 서버 구간과 재생 버퍼는 **포함되지 않는다**.
- 세션 구성: S1 ko→vi server_vad(무음 500ms) 5턴, S2 ko→vi semantic_vad(auto) 5턴(+S2b 재측정 3턴), S3 ko→vi 컨텍스트 정리 안 함 3턴, S4 vi·zh·ru→ko 각 1턴. 함정 문장(질문) 4개 포함.
- 원자료: `server/stream-measure-output/` (git 제외. `result.json`, `smoke/`, `s2b/`)

### 1-2. 지연 (말 끝 기준, ms)

| | 턴 | OpenAI 말 끝 감지 | 첫 번역 자막 | **첫 번역 음성** | 원문 전사 도착 |
|---|---|---|---|---|---|
| **server_vad** (무음 500ms) | 11 | P50 952 (911–1019) | P50 1560 (1235–1794) | **P50 1829 (1554–1994)** | P50 1798 (1477–2209) |
| semantic_vad (auto) | 5 | P50 1024 (1010–1435) | P50 1816 (1383–2200) | **P50 2056 (1697–2606)** | P50 1996 (1672–2355) |

- server_vad: 말 끝 감지 → 첫 음성 P50 850ms (585–1058). 감지까지 0.95초 중 0.5초는 설정한 무음 시간이다.
- semantic_vad는 더 늦고 편차가 크다(최대 2.6초). 문장 완결 판단의 장점(말 도중 쉼에서 끊지 않음)은 이번 문장들(쉼 없는 짧은 지시)에서는 드러나지 않았다.
- 한 턴에 응답이 둘로 쪼개진 경우는 없었다 (모든 턴 응답 1개).
- **휴대폰까지 넣은 예상**: 1.83초 + 휴대폰→서버·서버→휴대폰(같은 Wi-Fi, 약 0.05–0.1초) + 재생 버퍼(0.1–0.2초) ≈ **P50 약 2.0–2.1초**. 지금 발화 단위 방식(약 6초)의 약 1/3이지만 **계획 목표 P50 1.5초에는 못 미친다** (3절).

### 1-4. 컨텍스트(이전 대화) 누적

- 응답이 끝난 뒤 남겨 둔 이전 턴은 다음 턴 입력으로 다시 읽힌다. **이전 턴의 입력 음성은 음성 토큰으로**, 번역 출력은 **텍스트(자막) 토큰으로** 다시 읽힌다.
  - 이전 1턴 유지(S1): 입력 음성 토큰이 약 2배 (55 → 98), 입력 텍스트 +40토큰 → 턴당 약 +$0.0015 (+15%)
  - 정리 안 함(S3): 3번째 턴 입력 음성 141토큰 (3턴 누적), 그 일부(128)만 캐시 → 통화가 길어질수록 턴마다 선형 증가
- **결론: 응답이 끝날 때마다 OpenAI 세션 안의 이전 항목을 모두 지우는 것(유지 0턴)을 기본으로** 한다. 지우는 것은 OpenAI가 번역 문맥으로 들고 있는 내용뿐이고, 통화·지시 기록은 우리 DB에 지금과 같은 형식으로 저장된다 (지금 발화 단위 방식도 문장마다 세션을 새로 열어 이전 문맥을 쓰지 않는다). 문맥이 필요하면 이전 턴을 음성이 아니라 짧은 텍스트로 지시문에 넣는 쪽이 싸다 (S1에서 검토).

### 1-5. 번역 품질·함정 문장

- **함정(질문) 4/4 모두 번역만 하고 대답하지 않았다**: "오늘 작업은 몇 시에 끝나요?" → "Hôm nay công việc kết thúc lúc mấy giờ?", "이거 어떻게 하는 거예요? 방법 좀 알려 주세요." → "Làm cái này như thế nào? Hãy chỉ cho tôi cách làm.", 중국어·러시아어 질문 → 한국어 질문으로 정확히 번역.
- 숫자 보존: "2번 프레스", "3층", "오후 3시" 모두 유지.
- 음성→음성 번역이 원문 전사보다 정확한 경우가 있었다: 원문 전사는 "비계 → **기계**", "거푸집 → 커푸직/커푸지"로 틀렸지만 번역은 "giàn giáo(비계)", "ván khuôn(거푸집)"으로 맞았다. → **기록에 남는 원문(전사)에 현장 용어 보정이 필요**하다 (지금 `DomainProcessor` 보정을 전사 결과에 적용 + 전사 `prompt`에 용어 힌트). 
- 영문자 라벨: "B문"이 "cửa B / cửa phía sau(뒷문) / cửa bên(옆문)"으로 흔들렸다 (합성 음성 발음 영향 가능). 기계·구역 라벨은 실기기 실제 발화로 다시 확인.
- 어색한 표현: "안전고리를 꼭 거세요" → "phải móc móc an toàn"(móc 반복) — 원어민 검수 목록에 추가.
- 원문 전사는 첫 번역 음성과 거의 같은 시각(P50 1.8초)에 도착한다 → 화면 원문 자막은 번역과 비슷하게 뜬다.

### 1-6. 안정성 이슈 (1건)

- 1차 측정 S2(semantic_vad) 3번째 턴에서 번역 음성이 0.8초 나오다 끊기고 `response.done`이 오지 않았으며, 같은 세션의 다음 두 턴은 말 감지조차 없었다 → **세션 연결이 끊긴 것으로 보인다**. 그때 스크립트가 연결 종료를 기록하지 않아 원인은 확인하지 못했다. 같은 3턴을 다시 측정(S2b)했을 때는 정상이었다.
- 대응: 스크립트에 연결 종료·이벤트 기록 추가(이후 재현 없음). **S1 설계에 반영 필요**: 세션 중간 끊김 감지(close·응답 시간 초과) → 진행 중 턴은 실패 처리 + 새 세션으로 재연결, 반복 시 발화 단위 방식 폴백 (계획 4절의 장애 처리 그대로, 실제로 일어나는 일임을 확인).
- 그 턴의 일부 번역 음성 비용(약 $0.005 추정)은 `openai_usage`에 기록되지 않았다 (스크립트를 고쳐 이후에는 예상치로 기록).

**실기기 검증 순서 (제안)**

1. **react-native-audio-api 1.0 nightly** — 장기적으로 가장 유력. 확인: nightly 버전 고정 위험(1.0 정식 시점 불명), **Android 헤드셋 HFP 경로가 잡히는지**(안 되면 SCO/`setCommunicationDevice`만 담당하는 작은 Expo 모듈 추가), Oboe + VoiceCommunication에서 AEC 동작, iOS voice processing 켤 때 HFP 경로, `onAudioReady` 콜백이 끊김 없이 오는지.
2. **@speechmatics/expo-two-way-audio 0.1.2 + patch-package** — 6개 기능을 가장 빨리 확인할 기준선이자 포크 기반. 먼저 `EXFatal` 패치. 확인: 16kHz 고정(서버에서 24k→16k 변환), Android A2DP 기기 선택 시 예외 가능성, 재생 큐 스레드 안전성, 열린 이슈 #12(Android 13 잡음·AEC), #13(iOS 탭 중복 크래시), #9(작은 조각 재생 끊김), 첫 재생 후 2초간 마이크 입력을 버리는 동작.
3. (선택) @mykin-ai/expo-audio-stream — 경로 이벤트 비교용. Android 스피커폰 에코·BT 라우팅 없음 확인.

**모두 안 되면 자체 Expo 모듈** (speechmatics 코드를 포크해 시작하는 것이 가장 빠름): iOS는 한 `AVAudioEngine`에서 입력 voice processing + 같은 엔진 `AVAudioPlayerNode` 재생, 세션 `.playAndRecord` + `.voiceChat` + Bluetooth HFP, `AVAudioConverter`로 16k/24k 변환, 경로 변경·중단·미디어 서비스 리셋 처리. Android는 `AudioRecord(VOICE_COMMUNICATION)` + `AcousticEchoCanceler`/`NoiseSuppressor`, `AudioTrack(USAGE_VOICE_COMMUNICATION, MODE_STREAM)` + 쓰기 스레드·스레드 안전 큐·지터 버퍼, `MODE_IN_COMMUNICATION`, API 31+ `setCommunicationDevice`(그 이하 `startBluetoothSco`), `AudioDeviceCallback`, `BLUETOOTH_CONNECT` 권한. JS 경계는 `NativeArrayBuffer` 100ms 프레임, 이벤트 `onMicFrame`·`onLevel`·`onRouteChange`·`onInterruption`, 함수 `enqueuePCM`·`flushPlayback`·`setRoute` + config plugin.

이 표는 소스·문서 기준이며 **실기기에서는 아무것도 확인하지 않았다** — 2-2 절차로 확인한다.

### 2-2. 실기기 검증 절차 (휴대폰 연결 후)

준비물: Android 휴대폰(USB 디버깅 켬, USB로 PC 연결), 가능하면 iPhone(Apple 계정·영문 경로 빌드 필요), HFP 지원 블루투스 헤드셋, 같은 Wi-Fi.

1. 기기 연결 확인: `~/Library/Android/sdk/platform-tools/adb devices -l` 에 휴대폰이 보여야 한다. 디스크 여유 확인 `df -h /System/Volumes/Data` (빌드에 수 GB).
2. **시험 앱은 본 앱과 분리**한다 (본 앱 의존성을 건드리지 않기 위해): 영문 경로(예: `~/syncrew-audio-lab`)에 Expo SDK 57 빈 앱을 만들고 후보 라이브러리를 하나씩 설치·개발 빌드(`npx expo run:android --device`, JDK 21).
3. 각 후보에서 확인할 것 (항목마다 통과/실패와 수치 기록):
   - (a) 휴대폰 마이크 PCM 캡처: 프레임 간격·샘플레이트·음량 값
   - (b) 블루투스 헤드셋 마이크로 캡처 (헤드셋에 말한 소리가 들어오는지, 휴대폰 마이크가 아닌지)
   - (c) 캡처하면서 동시에 24kHz PCM 조각 연속 재생 → **헤드셋**으로 들리는지, 끊김 없는지
   - (d) 에코: 휴대폰 스피커로 재생하면서 캡처했을 때 재생음이 캡처에 얼마나 들어오는지 (재생 중 음량 dB 비교), 헤드셋일 때도
   - (e) 헤드셋 연결·해제 시 경로 변경 알림과 자동 전환
   - (f) 캡처 → 재생 왕복 지연 (손뼉 등으로 대략 측정), 10분 연속 동작 시 발열·메모리
   - (g) ③ socket.io-client로 PCM 조각(바이너리)을 PC의 시험 서버에 100ms마다 보내고 받기 — 지연·유실·base64 대비
4. 결과를 이 문서 2-3에 표로 남기고, D2(라이브러리 / 자체 모듈) 결정안을 적은 뒤 **S0 보고 → 멈추고 승인**.
